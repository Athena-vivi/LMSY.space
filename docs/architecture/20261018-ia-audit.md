# LMSY.space 内容与信息架构审计（2026-10-18）

> 范围：只读审计。未修改任何代码、数据、schema。
> 数据快照时间：2026-10-18 17:40（Asia/Bangkok 数据，查询走 Supabase 管理 API 只读通道）。
> 说明：本文是**迁移前**的快照，用于对照。迁移后的事实与数字见 `20261018-migration-log.md`（例如公开项目 26 → 21、无图公开项目 7 → 2）。

## 0. 结论摘要

1. **实体只有三层**：`projects`（26）→ `gallery_assets`（330）→ `profiles`（2）。没有作品表、没有人物关联表。所谓"作品"目前只是 `category='series'` 的两个项目。
2. **图片与项目关联是可靠的**：330/330 都有 `project_id`，0 孤儿。这是全库最健康的一环。
3. **图片来源是最大缺口**：`gallery_assets.source_url` 只有 18 条（5.5%），集中在 3 个项目（Affair 9 / MILESTONES_ARCHIVE 6 / airport 3）。其余 312 张无法追溯。
4. **发布状态形同虚设**：26 个项目里 24 条 `curation_status='draft'`，但全部 `portal_visible=true`，前台全部可见。可见性规则只看 `portal_visible && != 'archived'`，`draft` 本身不拦。
5. **分类值被 CHECK 约束锁死为 6 个**：`series / editorial / appearance / travel / daily / commercial`。目标 8 类必须先改约束才能写入。
6. **7 个项目 0 图片**（Harmony Secret、EVERAFTER BLOOM、3×Project 2026-03-15、Radar 10/15、Radar Feb 24），其中 5 个是采集容器/空壳，不是作品。
7. **三张表已废弃但仍在**：`gallery`（0 行）、`publications`（0 行）、`chronicle_events`（0 行）。前台没有任何一处读它们。
8. **人物只有一套数据源可用**（`profiles`，2 行），但前台有三套实现（`/profiles` 静态对照、`/profiles/lookmhee|sonya` 硬编码、`/profiles/[id]` 读库无入口）。

## 4. 指令中七个核实项的回答

### 4.1 同一后台项目是否被多页面重复展示

**是，而且严重。** 以下五个入口都在列同一批 26 行 `projects`：

| 入口 | 实际数据来源 | 与其它入口的关系 |
|---|---|---|
| `/projects` | `projects` 全量（公开过滤） | 母集 |
| `/exhibitions` | 按 `projects.category` 分组的计数 | 同一批，换个名字 |
| `/exhibitions/category/[type]` | `projects.category = type` | 同一批，按类切片 |
| `/editorial` | `projects.category = 'editorial'` | 同一批的子集，但走独立路由 + 独立封面字段 |
| `/search` | `projects` + `gallery_assets` | 同一批 |

`/exhibitions` 与其分类页本质上是 `/projects?category=` 的名字不同的版本；`/editorial` 是 `category='editorial'` 的专用视图。三处各自维护一套封面/计数/排序逻辑，已出现计数不一致（本阶段 T3 修过一次：4 期封面相对路径导致重复计数）。

### 4.2 图片能否可靠关联到项目

**能。** 330/330 `project_id` 非空，外键存在。唯一风险是外键是 `ON DELETE SET NULL`：删项目会把图片变孤儿而不是阻止删除。迁移期间必须禁止删项目。

### 4.3 每张图片的原始来源能否长期追溯

**不能。** 只有 18 张（5.5%）有 `source_url`。字段早已存在（`source_url` / `source_platform` / `source_account`），但采集链只在少数路径写入。`draft_items` 层反而有完整的 `source_url/platform/post_id`（82 条草稿里大部分有），说明信息在转正（to-gallery）时丢失了。

这是**已有字段但写入路径缺失**，不是缺字段。

### 4.4 人物、作品与项目是否真有数据关联

**没有。**

- 人物：`profiles` 独立 2 行，与 `projects` 无任何外键或连接表。旧表 `gallery.member_id` 是唯一的历史关联，但 `gallery` 已空。
- 作品：不存在 `works` 表。两部剧只是 `projects` 里 `category='series'` 的两行。同一部剧的剧照、宣传、活动无法聚到一部"作品"下——目前只能靠标题文本匹配。

### 4.5 日期字段是否混用

**是，三种日期混在一起：**

| 字段 | 实际写入内容 | 问题 |
|---|---|---|
| `projects.release_date` | 有时是剧集上线日，有时是杂志发行日，有时是采集日 | 被当作"事件日"用于编年史 |
| `projects.start_date` / `end_date` | 仅 7 条，语义与 release_date 重叠 | 实际未被前台使用 |
| `gallery_assets.event_date` | 已有 312 张从文件名推断，9 张今天修正为 2024-10-28；但修复前有 35 条微博草稿的 `event_date = created_at::date` | 值齐全但部分不是真实事件日 |
| `created_at` | 系统时间 | 唯一可靠的"入库时间" |
| `draft_items.raw_event_date` | 仅 0 条有值 | 原始文本日期未被保留 |

结论：**"值齐"不等于"语义正确"**。330 条 `event_date` 全部非空，但其中一部分是采集日。

### 4.6 分类是否存在空/重复/命名不一致

- 空分类（0 项目）：无（6 类都有项目）。
- 无效分类（有项目无图片）：`behind_the_scenes`、`early_archive` 尚不存在。
- 命名不一致：`series`（前台叫 Drama）、`appearance`（前台叫 Live / Stage）、`travel`（前台叫 Journey）、`daily`（前台叫 Daily）。数据库值、路由段、文案三层各叫一套。
- 前台筛选值与数据库值：`/exhibitions/category/drama|stage|travel|daily|commercial` 与 `category` 值 `series|appearance|travel|daily|commercial` **不一致**（drama→series、stage→appearance），中间靠 `lib/exhibition-categories.ts` 手工映射。

### 4.7 后台能否批量整理图片、能否看出缺资料

- 能：按批次筛选、单条/循环转正、编辑项目、上传。
- 不能：没有"缺来源/缺日期/缺封面/0 图片"的筛选与视图；没有重复图片检测（`file_hash` 只在 `draft_items` 有唯一索引，`gallery_assets` 没有 hash 列）。

## 5. 五类问题的归类

### A. 已存在且可以继续使用

`projects.id/title/category/release_date/description/cover_url/portal_visible/portal_priority/curation_status/title_i18n/description_i18n`；`gallery_assets.id/image_url/project_id/event_date/catalog_id/tag/title/caption/sequence/is_cover/source_url/source_platform/source_account/blur_data`；`profiles` 全字段；`site_content_blocks`。

### B. 已存在但需统一含义或用法

| 字段 | 现在 | 应改为 |
|---|---|---|
| `projects.release_date` | 混合语义 | 明确为"原始内容发布/上线日"，编年史不用它当事件日 |
| `projects.start_date`/`end_date` | 27% 有值，未使用 | 保留给"持续期项目"（如展览档期），或迁移后废弃 |
| `projects.catalog_id` | 0 使用 | 决定启用或删除 |
| `gallery_assets.title` / `caption` | 同值重复 | 保留 `caption` 为唯一说明，`title` 只在需要命名单图时用 |
| `gallery_assets.is_cover` 与 `catalog_id '-000'` | 两套封面规则 | 统一为 `is_cover` |
| `gallery_assets.tag` | Magazine/Advertising/STILL/STAGE/Telegram 混平台与内容类型 | 平台归 `source_platform`，`tag` 只留内容类型 |
| `gallery_assets.display_role` / `integrity_status` | 默认值填充 | 保留待启用，或迁移后移除 |
| `projects.curation_status` | draft 仍公开展示 | 明确 draft 是否可见（当前可见） |

### C. 确实缺失

| 缺口 | 影响 | 建议 |
|---|---|---|
| 项目 `slug` | 详情页是 UUID URL | 新增 nullable `slug`，唯一索引，回退 UUID |
| 项目事件日 | 编年史依赖 release_date | 新增 `event_date date null`，不用 created_at 兜底 |
| 图片来源写入链路 | 312 张无来源 | 改 to-gallery/upload 写入，不新增字段 |
| 人物↔项目关联 | 人物页无法列作品 | 新增 `project_people(project_id, profile_id, role)` |
| 作品实体 | 同剧多项目无法聚合 | 新增 `works(id, title, title_i18n, kind, ...)` + `projects.work_id` |
| 项目搜索别名 | 无法按别名检索 | 新增 `search_aliases text[]` |
| 项目 `updated_at` | 无法判断最近修改 | 新增 |
| 图片 `file_hash` | 无法查重 | 新增 nullable + 唯一索引 |
| 图片 `location` / `publisher` | 地点/出版方无处存 | 项目级新增 `location`、`publisher_brand` |

### D. 只需改前台，不需要动数据库

- 项目卡不再把 `catalog_id` 当主信息显示
- `/projects`、`/exhibitions`、`/editorial` 职责合并为"一个索引 + 分类筛选"
- 搜索结果显示所属项目而非内部编号
- 编年史改为"事件日优先、发布日次之、无日期不进时间轴"
- 首页门户口径与分类枚举统一

### E. 必须通过迁移才能解决

1. `projects_category_check` 约束扩容（6 → 8 值，或改名）。
2. 现有 26 行 `category` 值重映射（若采纳新枚举）。
3. 新增 `works` / `project_people` 表与外键。
4. `projects` 新增 `slug` / `event_date` / `search_aliases` / `updated_at` / `location` / `publisher_brand`。
5. `gallery_assets` 新增 `file_hash`。
6. 5 条采集容器项目的处置（保留为 `early_archive` 或标记 `is_container`）。
7. `curation_status` 与可见性规则对齐（是否让 draft 不可见）。

## 6. 迁移前必须知道的硬约束

```sql
-- 现有分类约束（扩容前必须先改它）
CHECK (category IN ('series','editorial','appearance','travel','daily','commercial'))

-- 图片外键：删项目不会阻止，会把图片变孤儿
FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE SET NULL

-- 唯一索引：首页精选仅允许 editorial 一条
UNIQUE (homepage_featured) WHERE homepage_featured = true AND category = 'editorial'

-- 图片编号唯一
UNIQUE (catalog_id)
```

## 7. 阻塞与风险

| 风险 | 说明 |
|---|---|
| 生产迁移权限 | 目前只有 Supabase 管理 API 的 SQL 通道（可 DDL），无独立备份快照能力。DDL 前必须先手动导出一份 `projects` + `gallery_assets` 全表 JSON |
| 分类重命名影响历史 URL | `/exhibitions/category/drama|stage` 等已存在的链接需要 301 或保留别名 |
| 数据语义不可自动修复 | 35 条 `draft_items` 的 `event_date` 是采集日，312 张图无来源；这部分只能标记待补，不能自动生成 |
| 人物关联无现成数据 | 没有历史关联可迁移，只能按项目标题手工判定（26 行可人工过一遍） |
