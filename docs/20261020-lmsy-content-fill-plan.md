### 1.1 先把之前算错的一笔改正

## 二、一条内容进库长什么样

### 2.1 必填与选填

| 列 | 规则 | 不填的后果 |
|---|---|---|
| `title` | 必填，见 2.2 命名规范 | 建不了 |
| `category` | 必填，七门对应值见第四节 | 落不进任何门 |
| `subtype` | 3/4/6 号门必填，门内分栏全靠它 | 分栏里看不见 |
| `event_date` | 必填（作品类用 `release_date`） | 时间线不出点、`/talks` `/live` 落到「日期未知」组 |
| `portal_visible` | **必须显式写 `true`**（默认 false） | 前台完全看不到 |
| `curation_status` | **必须显式写 `'published'`**（默认 draft） | 同上 |
| `description` | 一句话，50 字内 | 列表里只有标题，能看但干 |
| `location` | 有就填，查不到留空 | 不要编场馆 |
| `publisher_brand` | 品牌活动、品牌直播、代言必填 | 5 号门品牌墙分不了组 |
| `watch_url` | 有就填，没有留空 | 不出现外链按钮（页面不会假装能播） |
| `cover_url` | 有就填，没有留空 | 列表不显示缩略图，不影响可读 |
| `work_id` | **这轮全部留空** | 等 works 补齐后统一回填 |
| `tags` | 每批打一个批次标记，见第六节 | 不能按批回滚 |

`is_container`、`portal_priority`、`homepage_featured` 保持默认，这轮不碰。

### 2.2 标题规范

现有 20 条里有 `Sweet`、`Close`、`live`、`coffee`、`perla杂志`、`20241217【天津Fan sign PB】` —— 这些是自动抓取留下的，不是命名规范。

新内容的标题规则：

1. **不带日期前缀**。日期在 `event_date` 里，标题里再写一遍会让搜索和排序都乱。
2. **不用方括号包中文说明**。`20241217【天津Fan sign PB】` 这种写法是抓取器拼的，改成 `Fan Sign in Tianjin`。
3. **中文与英文不混写**。刊物名、活动名保留原文（`STARRY 星光画报` 可以，`perla杂志` 不可以 —— 改成 `Perla`）。
4. **活动名优先用主办方的正式名**，没有正式名才用「类型 + 城市」。
5. **单人场在标题里写清是谁**：`Solo Fan Meeting in Wuhan — Lookmhee`。

### 2.3 一条的样子（以见面会为例）

```sql
insert into lmsy_archive.projects
  (title, category, subtype, event_date, location, description,
   portal_visible, curation_status, tags)
values
  ('1st Fan Meeting in Manila', 'live_event', 'fanmeeting', '2025-03-15',
   'Aliw Theater, Manila, Philippines',
   'EVERAFTER 巡演第一站。',
   true, 'published', array['batch_20261021_live']);
```

## 三、三个阻断项，必须先处理

### 3.1 全部 8 份清单里没有任何一条链接

我把 8 份清单逐个搜过 `http`，**出现 0 次**。也就是说 `watch_url` 一个都填不了。

这意味着上线后的 `/talks` 和 `/live`：55 场直播只有「日期 + 平台 + 一句描述」，97 条对话只有「日期 + 媒体 + 节目名」，**没有一个能点开播放的按钮**。页面本身撑得住（列表式，无链接就不渲染按钮），但不是你要的效果。

处理方式是**分两轮，链接不阻塞建库**：

| 轮次 | 做什么 | 为什么这样排 |
|---|---|---|
| 第一轮 | 建记录，`watch_url` 留空 | 300 条的内容价值在「有这件事」，不在「能点开」 |
| 第二轮 | 按可补性补链接 | 补链接只 `update watch_url`，不动其他列，风险为零 |

补链接的难易排序（决定第二轮从哪开始）：

1. **直播 55 场** —— 最可补。这批内容当初就是从 B 站五个合集还原的，合集还在，逐场对日期即可。IG 那几场需要翻账号。
2. **综艺 21 场** —— 好补。平台和栏目名都在清单里（ONE 31、Workpoint、YouTube 频道），按「栏目名 + 日期」搜得到。
3. **访谈 63 条** —— 最难。43 条深度访谈只有「媒体名 + 日期」，很多是小频道，没有频道名就搜不到。建议只补能搜到的，其余留空。

### 3.2 约 300 条新内容几乎都没有封面图

库内 329 张图全部挂在那 20 条老项目上。新建的约 300 条基本是 `cover_url = null`。

`/talks` 和 `/live` 是列表式，没有图只少一个 48px 缩略图，**不影响可读**。但 3 号和 4 号门走的是 `/projects?category=...`，那个页面是**杂志大卡**：每张卡占两列、4:5 大图、标题 3xl–5xl。无图时显示一个 80px 图标占位。

**3 号门 60 个、4 号门 46 个巨大的灰色占位块，是这次填充最容易翻车的地方。** 三条路：

- **A. 让 3/4 号门也用列表式**（像 `/talks`）—— 最省事，一次改两行，但两个门会和对话/直播长成一样，首页七个门点进去四个都是列表。
- **B. 给大卡加降级**：无图时把卡压成一行紧凑条目，有图仍是 4:5 大卡 —— 保留杂志感，但混排里一行一条、一条一大卡会很跳。
- **C. 先只建有图的那几条** —— 3 号门只有 1 条、4 号门 2 条有图，等于不填。
- **D. 补图** —— 见面会 40 场的现场图，档案站和微博都有，但要逐场下载 300 张，是独立工程。

我倾向 **A**，但这是展示层决定，**要你点头才动**。可以先按 A 上线，等图补到一定量再切回大卡。

### 3.3 有一批内容还没有逐条清单

7 号门和 6 号门有完整清单（直播 55、综艺 39、采访 76），但 3 号门的两部分没有：

| 内容 | 状态 |
|---|---|
| 见面会 40 | ✅ `20261019-lmsy-fanmeeting-list.md` 全量 |
| 生日会 8 | ⚠️ 只有摘要，6 场有日期、2 场待补 |
| 品牌活动 12 | ❌ **没有清单**，只有「档案站 fanevents 三页共 12 场」这个结论 |
| 音乐 10 首、原著 3 本、奖项 15 项 | ❌ 没有清单，只有摘要 |

品牌活动那 12 场是我上一轮从档案站 `schedules/fanevents` 的三页（Party Events 4 / Local Events 4 / Brand Fansign 4）读出来的，只记了汇总，没落成表格，那份盘点文档已按你的要求清掉。

**所以建 3 号门之前，要先补一份品牌活动清单**，从档案站那三页拉一遍（品牌、日期、城市、店名）。工作量不大，一小时内能出。

| 5 | 三号门 单人见面会 12 + 生日会 8 | 20 | `batch_d5_solo` |

| 8 | 五号门 商务 | 41（45 − 现有 4） | `batch_d8_commercial` |

| | | **304** | |

`live_event` 现有 1 条要先核对是 60 场里的哪一场，属于的话第 4–6 批合计少建 1 条。

**回滚一个批次**：

```sql
delete from lmsy_archive.projects where tags @> array['batch_d1_interview'];
```

`p7_exec.py` 默认拒绝 `delete from projects`，回滚时要用它的显式开关（或先在快照表里核过再删）。

**批前快照**：每批插入前，先把当前 `projects` 全表复制到 `projects_before_batch<N>`。300 条约 1MB，成本可忽略。
